# Frontend Design 플레이북 — ezlong 신규 페이지 디자인 절차

> 출처: Anthropic 공식 `frontend-design` 스킬
> (https://github.com/anthropics/skills/tree/main/skills/frontend-design)
> 원문을 ezlong.com 의 기존 규칙(CLAUDE.md 29·31·33항, 라이트모드 절대 금지
> 목록) 위에서 쓸 수 있게 옮기고 각색한 문서다. 2026-08-10 작성.

## 핵심 한 줄

**코드를 쓰기 전에 미적 방향을 먼저 못 박는다.** AI 가 웹을 만들면 늘 같은
결과(Inter 폰트·보라 그라데이션·제네릭 히어로)가 나오는 이유는 방향 결정을
건너뛰고 바로 코드로 가기 때문이다. 방향 → 토큰 → 자기비평 → 코드 순서를
강제하면 뻔한 디자인이 사라진다.

## AI 디자인의 3대 디폴트 — 이것이 나오면 선택이 아니라 관성이다

원문이 지목한, 지금 AI 생성 디자인이 몰려 있는 세 가지 관성:

- 크림색 배경(#F4F1EA 부근) + 고대비 세리프 표제 + 테라코타 포인트
- 거의 검정 배경 + 형광 연두(acid green) 또는 주홍 포인트 하나
- 신문 조판풍: 헤어라인 괘선 + border-radius 0 + 빽빽한 다단

셋 다 어떤 브리프에는 정답일 수 있다. 문제는 **주제와 무관하게 나온다는 것**.
기획서가 이 중 하나를 명시했으면 그대로 따르되, 자유로 남은 축에서 이 세
가지로 흘러가면 관성이다 — 그 부분을 다시 정한다.

## 절차 — 브레인스톰 → 계획 → 자기비평 → 코드 → 재비평

### 1. 주제를 먼저 박는다

브리프가 주제를 안 박아주면 스스로 박는다: 구체적 주제 하나, 그 독자,
그 페이지의 단 하나의 임무. 독특한 선택은 언제나 **주제 자신의 세계**(그
분야의 도구·재료·용어·유물)에서 나온다. ezlong 이라면: 미국 주식, 차트,
티커, 캔들, 장 마감 시각, 분할 매매 같은 실물이 재료다.

### 2. 미적 방향을 하나 고른다 (코드 전에, 명시적으로)

Brutalist / Editorial / Retro-futurist / Luxurious / Maximalist / Organic /
Minimal-precision 등에서 이 페이지에 맞는 것 하나. ezlong 의 기본 축은
31항(Apple 여백·타이포 + visionOS 글라스 + 테슬라 미니멀)이므로, 보통은
그 축 위에서 "이 코너만의 변주"를 고르는 일이 된다.

### 3. 토큰 시스템을 압축해 적는다 (4개 항목)

- **Color** — 이름 붙인 hex 4~6개. ezlong 은 `ez-design.css` 변수 위에
  코너 전용 변수(`--sa-*`, `--wr-*` 방식)를 얹는 것이 우리 식이다.
- **Type** — 역할 2개 이상(표제/본문/캡션). **단, ezlong 은 웹폰트 금지**
  (29항, Manrope 2회 실패). 서체를 바꾸는 대신 **크기·굵기·자간·행간의
  스케일**로 표제의 개성을 만든다. 이 축은 우리 사이트에선 고정이다.
- **Layout** — 한 문장 서술 + ASCII 와이어프레임으로 안을 비교한 뒤 결정.
- **Signature** — **이 페이지가 기억될 단 하나의 요소.** 과감함은 여기
  한 곳에만 쓰고 나머지는 조용히 규율 있게 둔다. (스윙 AI 의 국면 띠 차트,
  이슈 코너의 마커 차트가 우리의 기존 시그니처 사례)

### 4. 계획을 브리프에 대고 자기비평한다

"비슷한 브리프를 받았어도 똑같이 나왔을 부분"이 있으면 그건 이 브리프를
위한 선택이 아니다 — 그 부분만 갈아엎고, 무엇을 왜 바꿨는지 적는다.
이 검증을 통과한 뒤에만 코드를 시작하고, 계획에서 벗어나지 않는다.

### 5. 코드 단계 주의점

- CSS 선택자 특이도(specificity)가 서로 상쇄되지 않게 구조를 잡는다 —
  특히 섹션 간 padding/margin 에서 `.section` 류와 요소 선택자가 충돌한다.
- 품질 바닥은 선언 없이 기본 탑재: 모바일 반응형, 키보드 포커스 표시,
  `prefers-reduced-motion` 존중. (33항 미준수 목록과 같은 자리)
- 만들면서 스크린샷으로 자기비평한다 — "그림 한 장이 토큰 천 개".
  샤넬의 조언: 집을 나서기 전에 거울을 보고 액세서리 하나를 뺀다.

## 디자인 원칙 (원문 요지)

- **히어로는 논지(thesis)다.** 주제 세계에서 가장 특징적인 것으로 연다 —
  헤드라인·이미지·애니메이션·라이브 데모·인터랙션 무엇이든. "큰 숫자 +
  작은 라벨 + 그라데이션 포인트"는 템플릿 답안이니 정말 최선일 때만.
- **타이포가 페이지의 인격을 진다.** 중립적 전달 수단이 아니라 그 자체가
  기억에 남는 요소가 되게. (ezlong 은 서체 대신 스케일·굵기로)
- **구조는 정보다.** 번호(01/02/03)·아이브로우·구분선·라벨은 콘텐츠의
  진실을 부호화할 때만 쓴다. 순서가 정보가 아닌 데 번호를 붙이면 장식이다.
- **모션은 의도적으로.** 흩어진 효과보다 잘 짜인 한 순간이 세다. 과한
  애니메이션은 오히려 "AI 가 만든 느낌"을 준다. 덜한 것이 나을 때가 많다.
- **복잡도는 비전에 맞춘다.** 맥시멀은 정교한 실행이, 미니멀은 간격·타이포·
  디테일의 정밀함이 필요하다. 우아함 = 고른 비전을 잘 실행하는 것.

## 카피(문구)도 디자인 재료다

- 화면의 말은 장식이 아니라 **이해를 돕는 재료**다. 간격·색과 같은
  의도로 다룬다.
- **사용자 쪽에서 쓴다.** 시스템 구조가 아니라 사람이 알아보는 이름으로.
- **능동태 기본.** 버튼은 눌렀을 때 일어나는 일을 그대로: "변경 저장"
  (Submit 아님). 같은 동작은 흐름 내내 같은 이름 — "게시" 버튼의 토스트는
  "게시됨".
- **에러·빈 화면은 분위기가 아니라 방향의 자리.** 무엇이 잘못됐고 어떻게
  고치는지. 에러는 사과하지 않고, 모호하지 않다. 빈 화면은 행동으로의 초대.
- 요소 하나에 임무 하나: 라벨은 라벨하고, 예시는 시연한다.
- (ezlong 추가) 우리 화면 카피 규칙이 위에 겹친다: '~하세요' 행동 촉구
  금지, 분석글은 명사형 개조식(34항), '—' 금지, 전문용어 금지, 비유가
  정보를 대신하면 금지(42항).

## ezlong 에서의 우선순위 — 충돌 시 이긴다

이 플레이북은 **절차**를 주고, 아래 기존 규칙은 **한계선**을 준다.
충돌하면 항상 기존 규칙이 이긴다.

- 웹폰트 금지 · 본문 16px(보조 14px) 하한 · 라이트모드 절대 금지 목록
- `ez-design.css` 변수 체계 + 코너 전용 변수 방식
- 글로벌 헤더/푸터(`ez-nav.js`/`ez-footer.js`) 필수
- 라이트/다크 두 모드 렌더 검증, 폰 폭 먼저
- 33항 apple-design 스킬 병용(그쪽은 모션·재질·타이포의 세부 기준)

## 신규 페이지 착수 체크리스트 (요약)

1. 주제·독자·페이지의 임무 한 줄씩
2. 미적 방향 1개 선언 (3대 디폴트 회피 확인)
3. 토큰 4종 작성: 색 4~6 / 타입 스케일 / 레이아웃 ASCII / 시그니처 1개
4. 자기비평: "다른 브리프여도 똑같았을 부분" 제거
5. 코드 (계획 준수, 특이도 주의, 품질 바닥 기본 탑재)
6. 스크린샷 자기비평 → 액세서리 하나 빼기 → 라이트/다크·폰 폭 재검증
